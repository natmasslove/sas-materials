# Solution Architecture School — материалы

## Цель

Программа менторинга по дизайну в Solution Architecture. Автор — архитектор, ведёт программу для своих менти.

- Главная цель: дать простой thinking framework для дизайна решений.
- Побочная цель: покрыть все существенные топики проектирования компонентов и сервисов.

## Рамки

| Пункт | Значение |
|---|---|
| Менти | Senior / lead инженеры |
| Группа | 2–3 человека |
| Объём | 8–10 модулей, 60–90 мин |
| Состав | Теория (обсуждение) + учебные кейсы |
| Домен | Нейтральный, акцент на Data Engineering. Без привязки к облаку и продуктам |
| Язык материалов | Русский. Стандартные архитектурные термины — на английском, без перевода |
| Кейс | Один сквозной на всю программу. Кейс уже есть у автора |

## Договорённости

- Фокус работы агента = теоретическая часть. Кейсы не разрабатывать, детали сквозного кейса не придумывать. В материалах писать «сквозной кейс».
- Подход: framework = хребет программы. Модули идут по шагам framework, топики подаются на том шаге, где нужны.
- Диагностики гэпов нет. Покрываем все существенные топики.
- Обязательно в программе: бизнес-требования, NFR, trade-offs.
- Формат = обсуждение, не лекция. Не каталог паттернов.
- Не цель: подготовка к интервью, глубокое изучение конкретных технологий.
- Data Engineering: расширенно в модулях 5 и 6. В остальных — один короткий пример (до 100 слов).
- Стандартные архитектурные термины не переводить: requirements, assumptions, constraints, risks, stakeholders, business drivers, scope, trade-offs, quality attributes, failure modes и подобные. Остальной текст — русский.
- Читатель — senior/lead. Базовое не объяснять.
- Чтение: раздела «Чтение» нет. Ссылки на книги в модулях не давать.
- Лимита слов на модуль нет.
- Homework = сквозной кейс, модуль за модулем. Итог всех homework = Solution Architecture Document (SAD).
- Выпускная работа = два артефакта по итогам всех модулей: SAD для сквозного кейса + работа по своей теме. Тема выбирается с менти в модуле 1 (артефакт, гайд или другое).
- Задания и просьбы к менти писать мягко: «рекомендуется прочитать», «желательно», не «читать», «обязательно».

## Framework

```
1 Context → 2 Requirements → 3 NFR → 4 Options → 5 Trade-offs → 6 Decision → 7 Risks
```

Названия шагов канонические. Использовать во всех материалах без изменений.

## Правила для новых материалов

- Перед работой прочитать `docs/2026-11-15_design.md` и `docs/2026-11-15_plan.md`.
- HTML-каркас страницы — копировать из `html/module-01.html`: `<head>`, `<nav>` сверху и снизу, `style.css`, скрипт Mermaid.
- Структура модуля — из плана. `<h1>` + строка «Шаги framework» + ровно 6 разделов `<h2>`: Зачем → Ключевые идеи → Пример: Data Engineering → Типовые ошибки → Вопросы для обсуждения → Подготовить к следующему модулю. Раздел «Подготовить к следующему модулю» — всегда список: (1) прочитать PPT-материалы следующего модуля; (2) прочитать конспект следующего модуля (ссылка на страницу, если она есть); (3) работа по сквозному кейсу. Исключение: модуль 1 имеет дополнительный первый `<h2>` «Старт программы» и не имеет строки «Шаги framework».
- Необязательный последний `<h2>` «Дополнительные материалы»: желательные, но не обязательные ссылки (видео, статьи). Добавлять только ссылки, которые дал автор. Свои не подбирать.
- Стиль и глубина — как в готовых модулях 1 и 2.
- Таблицы и схемы вместо сплошного текста. Таблица: `<div class="table"><table>…</table></div>`. Диаграмма: `<pre class="mermaid">…</pre>`.
- Не дублировать темы: таблица «Границы тем» в плане.
- Новая страница: добавить ссылку в `html/index.html`, обновить «Назад / Дальше» в `<nav>` соседних страниц.
- После написания страницы отметить шаг в плане (`- [x]`) и обновить таблицу «Статус» ниже.
