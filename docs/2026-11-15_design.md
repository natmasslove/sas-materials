# Программа менторинга: Solution Architecture Design

Статус: утверждён 2026-11-15.

## Цель

Дать senior/lead инженерам простой thinking framework для дизайна решений. По ходу покрыть все существенные топики проектирования компонентов и сервисов.

## Рамки

| Пункт | Значение |
|---|---|
| Менти | Senior / lead инженеры |
| Группа | 2–3 человека |
| Объём | 8–10 модулей, 60–90 мин |
| Состав | Теория (обсуждение) + учебные кейсы |
| Домен | Нейтральный, с акцентом на Data Engineering. Без привязки к облаку |
| Язык материалов | Русский |
| Кейс | Один сквозной на всю программу |

## Goals / Non-goals / Anti-goals

| Тип | Содержание |
|---|---|
| Goal | Менти применяет один и тот же framework к любой задаче дизайна |
| Goal | Бизнес-требования, NFR, trade-offs — в каждом модуле |
| Goal | Все существенные топики покрыты. Без предварительной диагностики гэпов |
| Non-goal | Разработка кейсов (кейсы уже есть) |
| Non-goal | Подготовка к system design интервью |
| Non-goal | Глубокое изучение конкретных технологий и продуктов |
| Anti-goal | Каталог паттернов без способа мышления |
| Anti-goal | Лекции. Формат = обсуждение |

## Подходы

| Подход | Суть | Решение |
|---|---|---|
| A. Framework = хребет | Модули идут по шагам framework. Топики подаются на том шаге, где нужны | **Выбран** (без диагностики гэпов) |
| B. Каталог топиков | Классический курс по building blocks, framework в конце | Отклонён: framework теряется |
| C. От кейсов | Теория подтягивается по ходу кейса | Отклонён: теория фрагментарна |

Причина выбора A: цель = способ мышления. Framework повторяется каждый модуль → запоминается.

## Framework (7 шагов)

```
1 Context → 2 Requirements → 3 NFR → 4 Options → 5 Trade-offs → 6 Decision → 7 Risks
     ▲                                                                          │
     └──────────────────────── итерация ───────────────────────────────────────┘
```

| # | Шаг | Главный вопрос | Артефакт |
|---|---|---|---|
| 1 | Context | Кто, зачем, в каких границах? | Стейкхолдеры, бизнес-цели, ограничения, context diagram |
| 2 | Requirements | Что система должна делать? Что влияет на архитектуру? | Ключевые сценарии, scope, допущения, список ASR |
| 3 | NFR | Насколько хорошо? В цифрах | Quality attribute scenarios, приоритеты, оценка нагрузки и объёмов |
| 4 | Options | Какие 2–3 решения возможны? | Декомпозиция, стиль, building blocks для каждого варианта |
| 5 | Trade-offs | Что получаем и что теряем в каждом варианте? | Матрица вариантов против NFR, стоимости, сложности |
| 6 | Decision | Что выбираем и почему? | ADR, диаграммы (C4) |
| 7 | Risks | Что может сломаться? Чего мы не знаем? | Список рисков, failure modes, план проверки |

ASR = architecturally significant requirement.

## Формат модуля (60–90 мин)

| Блок | Время | Содержание |
|---|---|---|
| Разбор | 15–20 мин | Домашний кейс с прошлого модуля |
| Теория | 30–45 мин | Обсуждение топиков. Менти читают материал заранее |
| Применение | 15–25 мин | Шаг framework на сквозном кейсе |

## Что делать дальше (после аппрува)

На каждый модуль — один HTML-файл (`html/session-NN.html`):

- ключевые идеи (1–2 страницы, таблицы и схемы);
- вопросы для обсуждения;
- типовые ошибки senior/lead инженеров в этой теме;

Плюс один файл-шпаргалка: framework на одной странице.

## Homework и выпускная работа

| Работа | Содержание |
|---|---|
| Homework | Сквозной кейс, модуль за модулем. Итог всех homework = Solution Architecture Document (SAD) |
| Выпускная работа | Два артефакта по итогам всех модулей: SAD для сквозного кейса + работа по своей теме. Тема выбирается с менти в модуле 1. Примеры: SAD для реального проекта; гайд (AI-assisted migration guide); другое по согласованию |

## Акцент Data Engineering

- Основной объём: модули 5 и 6.
- Остальные модули: один пример из data-платформ на модуль (NFR: freshness, data quality; надёжность: backfill, reprocessing; стоимость: storage против compute).
- Правило: пример, не отдельный курс. Framework остаётся нейтральным.
